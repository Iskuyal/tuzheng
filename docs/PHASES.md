## 各阶段的完成定义

### 阶段 0：项目基线

- 私有仓库可访问，默认分支含产品蓝图、路线图、阶段一任务和入口 README。
- `.firecrawl/`、依赖产物和环境密钥不会进入提交。
- 新会话只读上述文档即可知道阶段一做什么，以及尚未实现什么。

**验收记录（2026-09-25）：**[GitHub 私有仓库](https://github.com/Iskuyal/web-match) 的可见性与 `main` 远端提交已核对；首批文档的相对链接存在，`.firecrawl/` 和 `.env` 命中忽略规则，提交通过 `git diff --check`。阶段一尚未开发。

### 阶段 1：单图审计闭环

- 三个自制样例可从首页一键运行：算错、算对、看不清。
- 用户可上传图片、核对并修正模型读出的数值；程序在确认后计算增长率。
- 结果卡展示图内结论、数字、公式和不确定原因；无来源时绝不显示「事实已核实」。
- Windows 上 `npm install`、`npm run dev` 可启动；关键计算和结果分级有行为测试。
- 详细验收见 [STAGE-1.md](STAGE-1.md)。

**本地验收记录（2026-09-25）：**根目录 `npm install` 完成；`npm test` 为 **32/32 通过**；`npm run build`（含前后端 TypeScript 检查、Vite 构建和服务端编译）通过。Edge 浏览器逐个走查三个样例：矛盾样例按 80→100 算出 25% 并标记“图内矛盾”；一致样例标记“图内一致”；模糊值先显示“需要确认”，手动补入 100 后重算为 25%，并标记用户更正。图片可打开全屏放大并滚动检查细节；另验证着陆页 CTA、首页导航、样例卡和首页直接选图入口，确认文件带到审计页后由用户再点击读取；首页注明支持 PNG/JPG/WebP 和 5 MB 上限；设置页以替身密钥检查自定义 Responses URL／模型名的保存、重载、留空保留和清除，并确认读取接口不回传密钥；手动框选图片区域后，选区图像与对应文字摘录并排显示，竖版图裁剪框与实际选区对齐；上传新图在缺少密钥时显示明确提示。320px 与 390px 三页及展开菜单无横向溢出；390px 下导航改为独立菜单行，审计台桌面使用「图表／核对／结论」链接，窄屏改为一行当前图与步骤选择器；设置首屏摘要可见、完整说明可折叠；完整证据账本在手机端可收起并可从结论区直达。重新计算按钮留在完整表单之后，经浏览器断言确认不会盖住编辑框。键盘 Tab 可到达设置表单，焦点轮廓和输入标签可见；浏览器无页面异常。`npm install` 与 `npm audit --omit=dev` 均报告 0 个漏洞。

**独立视觉评审（2026-09-25）：**最近一次已完成评审是第 33 轮，得分 8.4/10，建议缩短窄屏固定步骤栏、在首页显示上传格式与大小，并让只读摘录和可核对数值更易区分。本轮已完成对应调整并通过本地走查；第 34 轮按同一提示委派后未返回评分。此前设定的 9/10 视觉门槛尚未达成，界面评审仍待继续。

当前图片证据链把原文摘录设为只读、把可确认数值设为可编辑，并为每条数据提供“回看原图”入口；图片放大视图提供左右平移控制，桌面步骤链接和手机端紧凑选择器连接图表、核对表单和结论。

**真实云端视觉读取验收记录（2026-09-26）：**本机设置页已保存真实 API Key（保存在当前 Windows 用户配置目录，接口只返回 `hasApiKey`）。用同一组团队自制 PNG 分别走服务端上传接口与页面「上传我的截图 → 读取整张图片」路径，均由 Responses API 结构化输出返回 `claims[]`：矛盾样例读到「年营业收入增长 40%」、2024 年 80 万元、2025 年 100 万元，确认后算出 25% 并判「图内矛盾」；一致样例读到标题 25% 与同样两个数值，判「图内一致」；模糊样例把 2025 年数值保留为 null 并在 `unreadableItems` 说明模糊标签，没有臆造数字（补值后仍按阶段一规则算出 25%）。单次读数耗时 3.2—4.4 秒（页面路径 5.0 秒，含上传与校验），模型为第三方 Responses 兼容端点的 `deepseek/deepseek-v4.1-flash`。模型响应中不含确认状态、计算值或结果状态。阶段一「实时视觉模型」一项据此通过；成本、其他图表类型的识别准确率与失败率仍未评估。

百分比对比口径为：程序计算值先保留两位小数，再与标题百分比精确相等才判一致。预置标题文字另有自动化检查，必须与对应 SVG 图片中的可见标题逐字一致。

### 阶段 2：读者工作台完善

规格与任务：[`spec.md`](../.scratch/stage-2-reader-workbench/spec.md)，以及同目录下按依赖顺序编号的 `issues/` 文件；首个任务的交接提示见 [STAGE-2-PROMPT.md](STAGE-2-PROMPT.md)。任务 01—03 已本地验收，任务 04 待开始。

- 一张图中的多个主张可分别确认、检查和更正；不能确认的主张保持待核对。
- 修改观察值后，相关结果重算，不相关结果保持不变。
- 用户理解「图内一致」「图内矛盾」「需要确认」及图内证据的提取、确认、缺失状态；移动端可完成核心路径。

**阶段二任务 02 验收记录（2026-09-26）：**新增每条主张独立的草稿值、确认值和结果；更正利润读数至 100 后只改变利润结果，收入结果保持“图内一致”；用户数补入数字后仍因图内依据缺失显示“需要确认”。`npm test` 为 39/39 通过，`npm run build` 通过；Edge/Playwright 走查完成三条主张确认、更正和局部重算，旧矛盾样例仍可计算。实时模型、会话操作记录与窄屏自动化仍待后续验收。

**阶段二任务 02 修复记录（2026-09-26）：**按截图复核发现主张卡底部文字缺陷：`确认并计算此主张` 按钮只在阶段一表单的 flex 列中被撑满宽度，主张卡换成普通块容器后按钮收缩为文字宽度，`confirm-hint` 的 -6px 上边距也不再被表单的 13px flex 间距抵消，提示文字因此压在按钮右下角（1441px 视口实测横向重叠 35px、纵向 6px，400px 以上窄屏为纯横向重叠）。修复：按钮显式 `width: 100%`，主张卡内按钮上边距 12px、提示上边距 7px。修复后实测 1441 / 800 / 390 / 320px 视口：按钮随容器撑满、提示与按钮间距 8px、无重叠、页面无横向溢出；阶段一表单间距不变（按钮距上一字段 15px、提示距按钮 8px）。`npm test` 39/39、`npm run build` 通过；三个阶段一样例重跑为矛盾样例 25%「图内矛盾」、一致样例「图内一致」、模糊样例补值后「图内一致」并标注用户更正。

**阶段二待补项（2026-09-26 审阅）：**主张卡的来源标记只在整图范围出现（“预置示例／模型读取”），每条主张的核对数值没有随字段显示“预置值／模型读取／用户更正”，阶段一表单已有的 `value-source` 标签未进入主张卡；用户更正目前只在确认后的结果理由里出现。规格第 15 行与用户故事 11 要求的“区分未确认观察、已确认或更正的读数、缺失证据并标明预置示例或视觉模型”因此只部分达成，需要在阶段二收尾前补齐。

**阶段二任务 03 验收记录（2026-09-26）：**每条主张记录确认、更正和重算的时间、动作、发生变化的值与对应结果，同一字段连续输入合并为一条更正，净变化为空的输入不记事件；主张列表上方提供一键「重置本次审计」，重置按最初载入的原始观察恢复草稿值并清空确认状态、结果和全部记录，计算在途时按工作区身份判定不写回迟到响应。实测：确认主张 1 记「图内一致」，主张 2 改 70→100 只留一条更正记录，更正主张 1 标题后重算显示「图内矛盾（此前为 图内一致）」；重置后主张 2 较新值回到预置的 70、三条主张回到「待核对」、记录清空；切换样例、重新载入同一张样例和刷新后记录都不保留，操作前后 `localStorage` 与 `sessionStorage` 条目数均为 0；320px 无横向溢出，重置按钮 40px 高可点。`npm test` 为 47/47 通过，`npm run build` 通过。阶段一单主张表单尚未提供记录与重置，需要时另开任务。

**阶段二任务 01 验收记录（2026-09-26）：**样例与 Responses 结构化观察均改为原始 `claims[]`；新增团队自制三主张预置图，旧三样例继续保留单主张确认与计算路径。`npm test` 为 37/37 通过，`npm run build` 通过；Edge/Playwright 本地走查验证首页四个样例、逐项展开证据、空 `claims[]` 不生成结论以及旧矛盾样例仍算出 25%。真实 Responses 调用未验证；当时任务 02—04 尚未开始。

### 阶段 3：跨图与视觉对照

- 两图仅在指标、时间、单位和范围一致时判定数值冲突；有歧义时主动要求确认。
- 柱状图纵轴截断以「可能误读」提示视觉风险，使用确认过的数值重画对照图；不武断判断动机。
- 两个能力各有正确、错误和歧义样例。

### 阶段 4：来源核验与竞赛深度

- 可手填数值或选择可公开使用的数据样例，清楚标注「用户确认」与「可追溯公开来源」的差别。
- 指标定义检索展示原文、出处和适用范围；至少用固定问题集记录使用检索前后的差异。
- Agent／工作流的工具选择、调用、失败与停止可展示；计算由程序完成，模型不执行任意代码。

### 阶段 5：稳定性与提交

- 团队自制的固定样例集覆盖算术矛盾、正确图、跨图冲突、视觉风险、模糊标签和缺失来源。
- 新机器按 README 启动；API 不可用时给出真实的失败提示，不以预计算结果冒充实时 AI。
- 提交材料满足赛题文档要求；先冻结演示路径，再录制视频和写技术文档。

## 两人协作方式

成员 A 主责读者流程、Vue 界面、样例图和演示；成员 B 主责模型适配、结构化观察值、计算与服务端。**每阶段以一条端到端功能验收**，两人都要用固定样例实际操作；不要把阶段拆成只完成前端或只完成后端的任务。

## 阶段结束时的记录格式

在对应阶段任务文档或本文件追加：完成日期、实际交付、运行命令、测试结果、人工验证样例、尚未验证的能力、影响下阶段的决定。计划项与已实现项须始终分开写。
