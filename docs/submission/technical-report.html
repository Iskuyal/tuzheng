一、项目概述

1.1 问题

社交平台和资讯站点上大量图表以截图形式传播。读者往往只有一张图，配文写在标题或正文里，出处要么没有，要么是一句「据国家统计局」。 读者要判断的其实是很朴素的两件事：图里写的东西自己是否自洽（例如柱高对应的涨幅和标题里的百分比对不对得上），以及 配文说的和图上、和可查的公开来源是否一致。这两件事目前都靠人肉：自己算一遍百分比，再去搜索官方发布核对口径。

更麻烦的是第二件事很容易做错。同一张 CPI 图，同比和环比可以是两个完全不同的数字；「上涨 0.8%」在 2025 年 12 月和 2026 年 8 月两个发布里同时存在，只看数值相等就下结论会得到相反的答案。普通读者既没有资料库，也没有逐条记录推理过程的工具。

1.2 目标用户

第一目标用户是只有截图的普通读者：他拿不到原始数据，也不打算做专业查证，只想知道这张图「能不能信、能信到什么程度、哪里需要打问号」。 这个定位决定了产品的三条底线：

  • 只检查有依据的部分。图上读不到、资料库没有的内容，一律给「需要确认／待核对」，不猜、不补。
  • 结论不越权。图内一致不代表现实数据真实；来源结论只说明「与所引发布是否一致」，不判断造假或作者动机。
  • 过程可复查。每条结论都要能点回到图上的抄录、模型读到的原文、程序算出的差值和所引用的公开材料。

1.3 产品形态与已完成的路径

应用在本机运行：npm run dev 同时启动页面与 API，浏览器打开 http://127.0.0.1:5173。四个页面：着陆页、审计工作台、来源核验、模型设置。

图内审计（阶段一—阶段三）上传或选用团队自制样例 → 模型读出图上原文与数值 → 用户逐条确认／更正 → 程序按公式计算增长率并判定「图内一致／图内矛盾／需要确认」；可放入第二张图做跨图口径比对，可对柱状图给出纵轴不从零的呈现风险提示。
来源核验（阶段四，本次主演示路径）上传图文 → 模型拆解主张（直接陈述／可检查推断／观点）→ 在固定国家统计局资料库里多轮调用受限工具检索与比较 → 程序校验引用与口径后给出逐条结论 → 缺关键口径时向用户提出一个具体问题 → 用户补充后沿同一条调查记录恢复 → 给出逐处有据的修改建议，由用户决定是否采用。
失败恢复（阶段五）区分未配置密钥、上游失败、超时、结构错误与格式不支持；失败时不展示任何旧结论或预置结果，给出可操作的下一步。

1.4 本报告不声称的能力

以下能力未实现或未验收，本报告与演示视频都不作为能力声明：
  • 固定资料库内的反证与版本复查（同一口径的冲突／修订来源对）——规划为条件增强任务，缺经核对的来源对，状态 needs-info，未实现。
  • 开放网络检索／通用 RAG／任意网页抓取——运行时只查构建期写死的三条材料，不访问开放网络。
  • 用户登录、协作、数据库、默认公网部署——本作品是 Windows 本机应用；公网演示为可选加分项，本报告记录决定与所需条件（见 6.4），本次不提供。
  • CSV／手填来源、MCP 协议集成——未实现。
  • Responses 协议下的工具循环在线验证——只有替身测试；在线验证使用 Anthropic Messages 协议。

1.5 一句话结论

在这张图 + 这几条可核查的官方材料的范围内，应用能给出带引用的分部位结论，能明确说出「哪一部分现在推不出来、缺什么才能继续」， 并且把模型能做的（读图、语义匹配、措辞提议）和必须由程序做的（计算、口径适配、引用校验、改写把关）分开—— 这套分工有 20 题 ×2 臂 ×3 次的真实模型配对评测记录在案（详见第六章与第七章）。

本章证据出处：能力清单与状态见 README.md「当前能力状态」表与 docs/PHASES.md；未实现项与阻塞状态见 .scratch/stage-5-stability-submission/issues/。

2.2 需求上的取舍

取舍理由
不做开放网络检索，改做「构建期固定的三条官方材料」开放网络检索无法保证「引用的材料确实存在、口径确实匹配、摘录没有被改动」这三件事；固定资料库带内容指纹与口径字段，能让「引用不在本次命中内」「口径不适配」成为可判定的程序规则而不是模型的自觉。范围换来了可验证性。
不做自动改写配文，只给建议并要求用户点击「采用」配文是用户的内容。程序只提议、逐处留痕、用户决定，避免「AI 悄悄改了你说的话」。
结论词汇限定为「与来源一致／不一致／待核对／推断依据不足／不支持核验」这五个词都是关于「与所引发布是否一致」的表述，不表达真假与动机；术语类主张因此只能到「待核对／依据不足」，这是有意保留的能力边界。
不引入数据库与前端状态管理库单机会话型应用，审计状态只存在于当前会话内存；减少依赖面与部署面，符合「Windows 根目录 Node/npm 可运行」的约束。

2.3 验收口径

项目自始至终使用同一条纪律：计划、实现、验收是三种状态。任务书里未勾选的项不得写进能力声明；真实模型结果、替身测试与预置样例分别计数；失败运行单列、不进分母、不删题。这条纪律本身也是作品的一部分（见第八章第 4 条创新点）。

本章证据出处：.scratch/stage-5-stability-submission/spec.md 的用户故事与实现决定；docs/PHASES.md 的阶段完成定义与逐条验收记录。

三、系统架构设计

3.1 技术选型

层选型理由
前端Vue 3 + Vue Router + Vite + TypeScript四个页面、一个工作台，组件数量不大；Vue 的单文件组件让「观察卡／结论卡／建议卡」这类结构重复、内容差异大的界面更好维护。Vite 提供秒级启动，便于「打开就能演示」。
服务端Node + Express 5 + TypeScript（tsx 运行）与前端同语言、同类型定义，模型适配器与领域层可以共享类型；只需一个 npm install 即可在 Windows 上跑起来。
领域层纯 TypeScript（shared/），零运行时依赖计算、判定、引用校验、建议校验全部是可单测的纯函数，看不到任何模型协议与 HTTP。
模型接入OpenAI Responses 兼容 + Anthropic Messages 两种协议各一个适配器避免被单一提供方锁死：设置页按协议分别保存地址、模型与密钥，在线验证用的是 DeepSeek 官方 Anthropic 端点。
存储无数据库；设置写入当前 Windows 用户的 LocalAppData，审计状态只在会话内存密钥不进仓库、不回传页面；会话数据刷新即清空，符合读者一次性核对的用法。

3.2 分层与数据流

三层结构：页面（web/）— 服务端（server/）— 领域层（shared/）。源码约 11 800 行 TypeScript／Vue（含样式），测试与端到端用例约 8 800 行。

目录职责
web/pages/着陆页、审计工作台、来源核验、模型设置四个页面；来源核验页把「输入 → 结论 → 建议 → 证据 → 轨迹 → 未解决项」按复查顺序排列。
server/app.tsHTTP 入口与端点；只监听 127.0.0.1。定义 VisionAdapter 与 SourceInvestigationDriver 两个窄接口。
server/source-investigation.ts受限工具循环编排器：预算、轮次、工具参数校验、轨迹记录、补证恢复、建议生成。
shared/source-audit.ts引用与结论校验、口径适配、原句追溯、主张分类、建议生成与逐处校验（约 2 200 行的纯逻辑）。
shared/source-library.ts固定资料库：三条材料的原始链接、发布机构、发布日期、适用口径、逐句摘录与内容指纹。
scripts/离线固定样例评测、在线配对评测入口、SVG→PNG 同源核对。

3.3 两个窄接口

VisionAdapter（图片读取）：Responses 用严格 JSON Schema，Messages 用强制工具调用；输入一张图，输出结构化观察值。 SourceInvestigationDriver（来源调查）：输入图片与配文，输出工具调用序列与最终汇总，支持沿同一会话恢复。 两个接口的共同点是领域层与页面都看不到协议差异——换端点、换协议不改判定逻辑，这是后续能用同一套评测同时覆盖两种协议的前提。

3.4 数据与隐私边界

数据存放位置说明
模型 API Key当前 Windows 用户的 %LOCALAPPDATA%\TuZheng\settings.json只由本机设置页提交给回环服务端；不读环境变量、不回传页面、不入仓库。读取接口只返回「是否已配置」。同一 Windows 账户下的其他进程也能读取该文件，README 已如实写明。
上传的图片仅在请求期间驻留服务端内存不写入项目目录；预置样例不发送到云端模型。
调查记录（引用、轨迹、结论）会话内存，服务端 30 分钟 TTL服务端以「图片＋配文指纹」兜底防止改输入后用旧结论（失配返回 409，过期 410）。
评测逐次记录仓库内 docs/evidence/*.json只含题号、结论、引用、工具序列与耗时，不含密钥与端点凭据。

3.5 与赛事提交要求的关系（环境变量与密钥）

赛题文档要求「API 密钥等敏感信息不得出现在公开仓库中，须通过环境变量方式配置」。本作品采用更严格的等价做法：仓库内不存在任何密钥，也不从环境变量读取密钥， 唯一的环境变量是可选的服务端口（.env.example 只有 PORT=3001）。密钥经本机设置页交给只监听 127.0.0.1 的服务端， 保存到当前用户的 LocalAppData，接口不回传。这样做的原因是：本应用是单机应用，密钥没有必要进入进程环境（环境变量会被子进程继承、也更容易被日志带走）。

本章证据出处：web/、server/、shared/ 目录结构与 README.md 的「技术架构」一节；密钥处理见 README.md 与 AGENTS.md 的「密钥与示例」约定。

四、AI 技术方案

4.1 选型理由：为什么是多模态模型 + 受限工具循环

  • 必须是多模态。输入是图表截图，模型要能读出「2025 年 12 月全国 CPI 同比上涨 0.8%」这样的图内原文。模型预设只收录支持图片输入的型号，避免接入纯文本模型后读图不可用。
  • 必须能调用工具。来源核验要「先检索、再比较、必要时问人」，这是多轮的、依赖中间结果的过程，单次问答无法表达「引用的是哪一条材料、用的哪个口径」。
  • 必须是结构化输出。观察值、主张、引用、建议都要能逐字段校验；两种协议都强制结构化（严格 JSON Schema／强制工具调用），并在提供方拒绝时按实测回退（DeepSeek 思考模式拒绝强制工具调用、GLM 类模型思考不可关闭——结构化请求先试「关闭思考 + 强制工具调用」，被 400 拒绝时回退「不关思考 + 自动工具选择」）。
  • 在线验证用的配置。Anthropic Messages 协议 + https://api.deepseek.com/anthropic/v1 + deepseek-flash，逐张图约 1.1—1.4 秒、整次来源调查中位约 5—7 秒。这一配置写在证据记录里，评测脚本在开跑前会核对协议与模型，配置不符直接拒绝运行。

4.2 集成方式：一次来源调查里到底发生了什么

一次来源调查（investigation）的完整约束如下——这些数字是代码常量，评测脚本逐项比对后才允许开跑：

约束取值作用
可用工具4 个search_source_library（检索固定资料库）、compare_values（确定性数值比较）、request_clarification（请求用户确认，最多 1 次）、report_source_finding（汇总，出口）
每轮工具调用上限3 次超出的调用不执行，并连同原因写进轨迹（页面上显示为「未执行」的黄色条目）
单次调查调用总预算6 次检索、比较、追问计入；汇总为出口不计入。达到上限后保留已核验结论，并列出未完成部分
轮次上限4 轮防止无限循环
整体时限150 秒超时按上游超时分类提示，不产出结论
单次可核验主张最多 3 条超出部分与模型声明未展开的内容按原文列出，按出处分「配文未展开／图上说明」，不静默丢弃
补证恢复与初查共享同一组预算恢复不能把预算清零；引用与结论按本轮主张口径重新校验

4.3 程序把关之一：引用与结论不由模型说了算

模型只能「提出引用」，能不能成立由程序按固定规则判定，规则本身可以单测：

  1. 在不在本次命中内。引用不在本次检索命中里的 ID 一律降级「来源待核对」；引用了资料库中不存在的 ID 记为虚构引用，引用了存在但不在本次命中内的另记「凭记忆复用」，两类分开统计。
  2. 角色是否与材料类型相符。引用一份材料时模型要声明它的角色：数值依据 / 术语解释 / 仅作背景。术语解释页只能解释「同比与环比有什么不同」，不能为某个具体月份的数值背书。
  3. 口径是否适配（按主张判定，不按检索查询判定）。只有指标、月份、范围都匹配的数据发布才能作为数值依据。这一条曾经按「检索时用的查询口径」判定，在真实评测里造成「模型引用了正确月份的材料却被程序拒绝」，修复后改按这条主张自己的指标／月份／范围判定。
  4. 原句能不能追溯到出处。配文主张必须能在配文原文里找到（文字重合度下限，且其中数字必须出现在配文或图上）；图内主张必须带图上逐字抄录，且所填比较方式要能在抄录里看到——这条规则是因为实测发现模型会给图上的数值补一个图上没写的「同比」，从而凭空把「待核对」变成「一致」。
  5. 值对不上不等于整句成立。推断类主张按「数字与口径」「推断结论」两个部位分别给结论；数字一致但推断方向被来源否定时，整条主张判「与来源不一致」。
  6. 措辞不越权。结论文案固定为「与所引国家统计局发布不一致」，不写「造假」「误导」，也不判断作者动机。

4.4 程序把关之二：修改建议由程序逐处生成与校验

核验结束后，程序按当前有效结论生成建议配文，每一步都关联证据：

主张状态允许的改动类型规则
与来源一致保留原句不得改写、不得删除（模型提议改写已核实内容会被拒）
与来源不一致替换数值只能用所引来源同口径的正确数值改正；不得保留错误数值（例如把环比 0.8% 改正为官方环比的 0.2%）
来源待核对保留并限定 / 建议删除必须保留限定语（如「暂未核实」）或建议删除，不得写成确定表述
推断依据不足保留并限定 / 建议删除同上，并说明缺哪一项依据
观点（不支持核验）保留原句 / 建议删除不做真假改写

模型可以在汇总里可选地附上自己的改写提议，但每条提议都要过一遍逐处校验：不得引入原配文、本次主张与所引来源之外的数值、月份、范围或因果／加强表述； 不合格的提议连拒绝原因一起留档，改动退回程序生成的兜底建议；提议字段本身畸形（不是数组、条目不是对象、超限）不会让整份汇总作废。

五、核心功能实现

5.1 图内审计：模型只读，程序才算

「模型只读不算」是第一条产品规则：模型负责读图、提取原文与数值、做语义匹配；所有百分比、差值、单位换算和结论判定都由确定性代码完成。 读图提示词明确禁止模型给出确认值、增长率或结果状态；模型输出先经 Zod 结构校验、再由用户逐条确认，才参与判定。

5.2 来源核验：本次主演示路径

主演示路径为「上传图文 → 主张拆解 → 工具检索 → 推断检查 → 必要补证 → 修改建议」。下面按界面顺序说明每一段做了什么、依据是什么。

（1）输入与主张拆解

上传图表截图（或载入团队自制样例）并填写配文。模型把配文拆成三类主张：直接陈述（原文直接写出的事实或数值）、可检查推断（由原文推出、原文没有直接写的结论）、观点（对原因、动机、价值或未来走势的判断）。观点标为「不支持核验」，系统不对它做真假结论。

（2）工具检索与逐条结论

模型在四个受限工具中自行选择：检索固定资料库、比较数值、请求用户确认、汇报结论。程序校验工具名与参数，按轮次与总量计预算，被拒绝的调用同样留在轨迹里。结论分部位给出，并逐条关联依据：

（3）必要补证：把「回答不了的问题」交给用户

当配文没写比较方式、而资料库里同比与环比的发布都在时，资料库回答不了「这句配文说的是哪个口径」——这正是必须问人的问题。 程序要求：先自己检索，检索后仍缺且会影响结论时，提出一个指向具体主张与具体字段的问题；反过来，资料已经覆盖的问题（配文自带口径与数值）不允许追问。 用户回答标为「用户提供」，只用于确定口径：图文没写的才填入；图文已写且与回答冲突时不覆盖、保留双方并降级为「待核对」、同时请求更正；回答解析失败不套用并说明原因。

（4）修改建议、采用与撤回

建议不自动替换原配文。用户点击「采用」后建议才写入配文输入框，同时旧结论与旧建议转入「历史结论（仅作历史展示）」，并要求重新核验；此后任何输入改动、重新核验或被补证结果接续，都会让旧建议立即失效并只作历史展示，历史条目保留其依据快照指纹。

（5）无适用来源与证据不足时的表达

资料库没有对应月份、或推断缺少必要依据时，结论保持「来源待核对／推断依据不足」，并明确写出「缺哪一项才能继续」「不代表结论为假」。数据边界同时显式声明：固定资料库共三条材料，干扰项与术语页会被排除并给出原因。

6.2 真实模型评测方法：不设「预留题」，但把口径写死

评测的目的不是产出一个漂亮分数，而是让「检索到底带来了什么」可被反驳。做法：

  • 题集与期望分开冻结。输入（图片、配文、图上声明文字、图片双指纹）在 samples/source-audit-questions.json，独立期望在 samples/source-audit-expectations.json；期望由人先于任何模型运行写定，不由模型生成、也不按运行结果回填。旧题的哈希有校验和守护，改写即测试失败。
  • 配对对照。同一模型、同一题集、同一资料版本下只改变检索工具可用性：无检索臂由服务端把检索工具从声明里移除，编排层同时拒绝任何检索调用（不执行检索、不回落命中），并要求模型写清缺少可用来源的原因。
  • 三个维度分别报告。事实正确性（主张状态是否正确）、证据可追溯性（接受的引用条数与角色、被拒引用及原因，无检索臂恒为 0）、不适用来源识别（干扰项与术语页的排除、越界结论次数），不把引用能追溯当成准确率提高。
  • 允许无检索臂答对。无检索臂给不出确定结论时，正确答案本来就是「来源待核对」——这类题目会「免费」答对，记录里逐题列出，不隐藏、也不据此宣称无检索有价值。
  • 评测侧独立复算。修改建议的「不得引入新事实」不依赖服务端校验实现，评测脚本按原始载荷独立重算一遍（数值、月份、范围、加强表述、未解决主张是否保留限定）。
  • 失败运行单列。不进分母、不删题、不用预置或缓存结果顶替；失败原因（含提供方 HTTP 402 余额耗尽）逐轮记录。

7.2 检索对照：无检索臂在哪些题上「免费答对」

无检索臂并非全错。在阶段四 05 的整组里，无检索臂 19/62 通过，其中 6 题 3/3 全对——这些题的正确答案本来就是「来源待核对」或「推断依据不足」（资料库没有适用来源、或配文没写口径）， 无检索臂无法给出确定结论，因此与期望一致。记录逐题列出这类「免费答对」，不把它藏起来，也不据此宣称无检索更有价值：配对差 62.9 个百分点全部来自资料库确实覆盖的那几题。 同时，检索臂退化题 0 题——没有出现「有检索反而比无检索差」的题目，也没有为了让无检索臂显得更差而调整题面或期望。

7.3 仍然成立的局限（逐条保留，不删题）

  1. 题型是开发题，没有预留题。四批评测的题集都由团队自制并在开发过程中扩展，不存在「先调好再考的留出题」，样本量不足以给出通用准确率。
  2. 只验证了一个模型与一种在线协议。deepseek-flash + Anthropic Messages；Responses 协议的工具循环只有替身测试。
  3. 模型行为漂移如实记录。q18（缺比较方式 → 应先检索再追问）：阶段四 04 有检索臂 3/3、05 为 2/3；未追问的运行判未通过且不编造恢复记录。q11 出现过模型给配文主张补了图上才有的比较方式（程序无法区分「配文写了」与「模型补的」）。q14 一次没填推断方向、q16 两次汇总缺必填字段导致无结论。
  4. 加强表述拦截有覆盖边界。词表能拦已知的因果／程度加强表述与中文数字范围，但实测出现过的「略贵」这类措辞不会被识别。
  5. 术语类主张只能到「待核对／依据不足」。结论词汇不表达「与术语页矛盾」，这是有意的能力边界。
  6. 补证恢复在线样本小（有检索 3 次、无检索 2 次）；补证回答解析只覆盖「同比／环比、YYYY-MM、数值、范围／指标原文」这类写法。
  7. 无检索臂的上游失败率曾高于有检索臂（阶段四 02：17/108 对 5/108；03 轮末尾确认是余额耗尽）。这一不对称在样本内稳定出现但原因不能断定，只作观察记录。
本章证据出处：上述每一条局限都能在对应证据记录的「不能外推、尚未验证的部分」小节找到原文；逐次运行 JSON 保留每题每次的结论、引用、工具序列与失败原因。

八、创新点

8.1 技术创新

创新点具体做法可核对的证据
1.「模型提议、程序把关」的受限工具循环 模型能用的只有四个工具，且工具名、参数、每轮与总量预算都由服务端逐个校验；被拒绝的调用不执行但连原因留档；最终汇总里的引用、结论与改写提议全部要过程序规则。模型只负责它擅长的：读图、语义匹配、措辞提议。 工具轨迹界面与 e2e 断言；「被拒绝调用」与「被拒提议」在整组评测里各有实测记录（阶段四 05：42 条提议被拒并逐条留档）
2. 把「口径」变成程序可判定的规则 只有指标、月份、范围都匹配的数据发布才能作数值依据；术语页只能解释比较方式；口径按主张自己的字段判定而不是按检索查询判定。同值干扰项（两个发布同比都是 0.8%）因此可以被程序区分。 固定资料库的干扰项设计；被拒引用逐条给出「口径不一致（月份／范围）」原因
3. 意图可用性的对抗性规则 三条规则直接来自实测踩坑：图内比较方式必须出现在图上抄录里（防模型凭空补口径）；配文主张必须能追溯到配文原文（防把来源原句当成用户的话）；未解决主张在建议里必须保留限定或删除（防把不确定写成确定）。 三条规则各有单测；q04、q18 等题在真实运行中的表现为「待核对 → 用户补证 → 一致」或「必须保留暂未核实」
4. 有对照、有失败、有独立复算的评测方法 有／无检索配对对照；期望先写、题集冻结、旧题哈希守护；允许无检索答对并逐题列出；失败运行单列不进分母；建议的「新事实不变量」由评测侧按原始载荷独立复算，不依赖服务端实现。 四批整组记录与逐次运行 JSON；阶段四 05 的两臂 124 次有效运行 0 次违反
5. 证据边界的界面表达 结论不是一句话，而是「分部位状态 + 依据原句 + 当前有效引用 + 未解决项 + 本次排除的材料及原因」；历史结论与当前结论物理分开，历史建议标明依据指纹「不代表当前结果」。 来源核验页的区块顺序与 e2e 断言；采用／撤回用例

8.2 应用创新

  • 把「核实」拆成读者能自己复走的动作。不是给一个「可信度 82 分」的黑箱结论，而是把过程摊开：图上写了什么、模型读到什么、你确认了什么、程序算了什么、引用了哪份材料、哪些没解决。读者可以只信自己能复查的那部分。
  • 把「不知道」做成一等公民。「来源待核对」「推断依据不足」「不支持核验」都是正式结论，界面不允许把它们写成确定表述；「本次没有核验的内容」有独立区块与覆盖度提示。
  • 面向传播场景的克制。对普通读者最危险的情形是把话说满——所以系统在缺依据时主动降级，并且在页面上说明「不能作为造假判断」。产品立场是帮助读者提问，而不是替读者定罪。
本章证据出处：创新点 1—5 的实现分别见 server/source-investigation.ts、shared/source-audit.ts（引用校验、建议校验）、scripts/evaluate-source-audit.ts（评测侧独立复算）与 web/pages/SourceAuditPage.vue。

九、总结与展望

9.1 已经做到的

  • 完成了一条端到端的、可在本机复现的图文来源核验路径：上传图文 → 主张拆解 → 工具检索 → 推断检查 → 必要补证 → 修改建议，并且每一段都留下可复查的记录。
  • 把「模型能做什么」和「程序必须做什么」分开，并用一套可重复的评测去看这条分工是否真的有用：20 题 ×2 臂 ×3 次的整组对照里，有检索臂主张状态正确率 93.5%，无检索臂 30.6%，虚构引用与越界结论均为 0。
  • 把失败与边界做成产品的一部分：错误分类提示、失败不展示结论、未解决项单列、建议只能由用户采用、旧结论立即失效并只作历史展示。
  • 材料与实现对齐：本报告出现的每个数字都能指到一条命令或一份证据记录；未验收的能力（反证与版本复查、公网演示、Responses 协议工具循环）明确排除在结论之外。

9.2 做不到的（在本次提交里如实保留）

  • 不能判断现实数据真伪，也不能判断作者动机；来源结论只说明「与所引发布是否一致」。
  • 不能覆盖资料库之外的领域：只有 CPI 专题的三条公开材料，运行时不访问开放网络。
  • 不能给出通用准确率：题集是开发题、没有预留题，样本量不支持外推。
  • 不能保证模型行为稳定：追问率、主张条数、字段填写在不同运行之间有漂移，代码里能做的只是让它可见、可判、可失败。

9.3 下一步（按价值排序）

  1. 固定库内的反证与版本复查（需先找到经核对的同口径冲突／修订来源对）：这是目前最影响「可信度判断」的缺口，但必须等来源对可核对后再做，否则就是把猜测写进结论。
  2. 把在线评测扩到 40—60 题并引入预留题：现有题集把机制压测得比较充分，下一步要的是「没被调过的题」上的表现。
  3. Responses 协议的工具循环在线验证：目前只有替身测试，补齐后「双协议」才是完整的能力而非接口形态。
  4. 公网演示的密钥方案：若决定提供在线演示，需要先定义平台侧代管密钥或一次性体验额度、限流与可用性承诺，再谈部署。
  5. 建议的采用／撤回在真实模型下的体验复验，以及更自然的「加强表述」识别（词表之外的措辞）。

9.4 一句话

图证想做的不是「让 AI 告诉你这张图是真的」，而是让 AI 把可核对的依据摆到你面前，并诚实地标出它自己也不知道的地方。

本章证据出处：局限清单与下一步来源：docs/PHASES.md 阶段四、阶段五各节；docs/STAGE-5-PROMPT.md 的「未完成清单」；各证据记录的「不能外推」小节。
