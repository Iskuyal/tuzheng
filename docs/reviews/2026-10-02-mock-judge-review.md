## 3. 模拟评委评价

### 作品最能成立的技术主张

**“模型负责判断下一步要查什么，程序负责核对依据是否支持结论。”** 这是作品最值得保留的叙事。

- 单图路径中，模型提取观察值，人工确认后程序计算；能复核为什么80到100是25%。
- 来源路径中，模型选择检索、比较、追问和汇总工具，服务端验证工具名、参数与预算。
- 检索命中还须对齐指标、月份、范围和比较方式；同值、术语页或错误月份不能自动当作数值依据。
- 补证标为用户提供，继续同一调查；输入改变使旧结论与建议失效。
- 改写逐处关联原文与当前证据；数值、方向与新增事实受到程序约束，由用户明确采用。
- 版本替代依据明确官方修订声明，而非只因新旧数字不同就覆盖旧资料。

这些能力已经超出一次“发图给模型，再展示答案”的调用。组合本身未证明算法首创，但有可审查的工程与交互价值。

### GitHub 仓库会给评委什么印象

Git历史、中文提交、PR、CI、固定样例、独立期望和逐次模型记录组成了较好的开发证据。技术材料能追溯到源码及历史，且如实保存失败，这有助于评委复核。

弱点是入口像开发交接文档：README 首段和后文混有早期阶段、反复 UI 评审轮次与大量历史指标；`PHASES.md` 顶部仍写 PR #31 未合并，虽然当前实际已合并。历史记录应保留日期，但评委入口应先看到当前能力、运行方式、演示、最新限制与同一个提交基线。开发过程中的“9/10 UI门槛”也不能当作外部赛事评分。

仓库当前 PRIVATE。私有本身不违反规则，只要评委有访问权；本次没有发现已经授予评委权限的证据。视频尚无成品链接，README 团队仍为成员A/B占位。

### 作品体验会给评委什么印象

桌面和手机布局已具备完整作品外观；原图、确认数值、公式、历史状态的关系清楚。无需新增一套视觉风格。

不过首页主视觉和11个样例主要展示图内、跨图与纵轴；最强的来源调查入口主要在导航中。评委若只顺着首页使用，可能只看到确定性算术检查。建议给来源主线一个醒目的演示入口。来源页出现“阶段四”、工具校验等开发表达，首段解释较长；面向读者可先说“核对配文与公开来源”，再按需展开技术说明。设置页的大量预设也应让位于“本项目实测配置”和协议验证边界。

当前没有实时工具事件流，只在返回后展示轨迹。这不否定 Agent 实现，但长等待中评委难以看到行动过程；若做增量显示，应来自服务端真实事件，不能用预设动画冒充工具进度。

## 4. 最影响评分的证据问题

### A. 演示稳定性叙述早于最新记录

README 与演示脚本使用“冻结五题各3/3通过”的早期记录。最新22题原始JSON显示：

| 演示相关题 | 最新检索臂结果 | 解释 |
| --- | --- | --- |
| q18 必要追问与恢复 | **2/5个阶段运行通过** | 初查3次、触发恢复2次；有一次未追问，另有主张匹配/补证套用问题；不能当作5次完整端到端试验 |
| q20 两处修改建议 | **2/3运行通过** | 一次运行缺少符合期望的配文主张及建议改动等；不能仅概括为数值替换错误 |

这不证明当前修复后仍然失败，但足以说明历史3/3不能代表最新演示稳定性。既有脚本也有追问率漂移的说明，应把主表和录制前条件统一到当前实测。

### B. 89.7%并非陌生截图准确率

本次离线复算确认检索臂61/68=89.7%、无检索臂19/69=27.5%，平均耗时分别6723ms与5472ms。判定涵盖状态、引用、追问、补证、建议等，是整次运行通过率；初查与恢复分别作为记录。存档报告的“虚构引用0、越界0”描述该批样本，不是系统在所有输入上的保证。

无检索臂既没有资料，又不允许凭模型记忆引用。因此差异主要说明“获得适用来源后，受证据约束的工作流能完成任务”，不能宣称比普通聊天模型事实判断准确率提升62.2个百分点。最新PDF已准确解释这一点，应保持同一口径。旧证据记录仍有“主张状态正确率”“额外耗时=0”等历史用语，答辩时采用新PDF定义。

### C. 仍缺当前版本和真实用户证明

本地全绿不能替代修复后真实模型复验。存档JSON没有足够的代码SHA及完整快照绑定；目前也没有独立预留题、陌生用户任务、省时或错误减少数据。评委可认可工程能力，但不能据此认可通用可靠性或商业有效性。

### D. 提交要求尚未闭合

官网要求密钥通过环境变量配置，而当前代码与AGENTS明确采用设置页写LocalAppData且不从模型密钥环境变量读取。这是具体文字要求的差异，不是密钥泄露发现。需要后续产品决定：提供最小服务端环境变量兼容方式，或取得组委会对当前方式的认可。本次评审不修改这条项目约定。

仓库评审权限、视频成品和团队信息也仍待补。公网演示是可选项，缺少公网部署不应写成违反必交要求；目前部署文档只证明方案存在，不能算服务上线。

## 6. 建议答辩主线与评委追问

7分钟演示可按以下顺序：30秒说明截图读者的困境；60秒展示图内25%与标题40%的矛盾；90秒展示同比/环比来源错配及实际工具轨迹；60秒展示一次必要补证；60秒展示带引用修改及输入改变后失效；60秒解释最新评测、一个真实失败与边界；60秒交代目标用户、验证结果和收尾方向。录制前应按当前SHA真实跑通，失败不能剪成“每次都成功”。

| 评委可能追问 | 当前应答与待补证明 |
| --- | --- |
| 规则做了这么多，AI到底做什么？ | 展示图文提取、主张语义与工具选择；程序承担算术和证据资格校验，明确各自职责 |
| 固定五条资料是否只是演示？ | 承认领域原型；指出运行时真实检索与错误来源排除；用独立题和适用来源扩展证明复用性 |

## 7. 竞争力判断

核心路径具备值得进入认真评审的技术证据。79分反映“技术与交互机制较完整，验证和提交仍有缺口”。若只补交材料并对齐当前版本，主要是消除交付风险；若同时补独立评测、基线和真实用户任务，主观模拟评价有机会进入85分左右。该目标不是保证，各维度必须由新增证据重新评分。

在不知道参赛组别、同场作品及实际评委口径时，不能判断一等奖概率。赛事收尾应围绕可复核技术链、当前可靠性与用户收益集中投入；现有16页PDF结构已能服务此目的，不需要继续扩写开发过程。

本次新增此评审报告；产品代码、设置、历史证据与现有提交材料未改动。报告尚未提交或推送。
